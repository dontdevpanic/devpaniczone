Was ist Git?

Git ist ein verteiltes Versionskontrollsystem, das 2005 von Linus Torvalds (dem Erfinder von Linux) entwickelt wurde. Es trackt Änderungen an Dateien und ermöglicht dir, zu jedem gespeicherten Zustand zurückzukehren.

Wie Git funktioniert

Git erstellt einen versteckten .git-Ordner in deinem Projekt. Darin speichert es:

  • Snapshots - Momentaufnahmen deiner Dateien (nicht komplette Kopien, sondern nur Änderungen)
  • Timeline - Chronologische Historie aller Commits
  • Metadaten - Wer hat wann was geändert

Warum Git?

  • Sicherheit - Nie wieder Datenverlust, jeder Zustand ist wiederherstellbar
  • Speichereffizient - Speichert nur Unterschiede (Deltas), nicht komplette Kopien
  • Branching - Experimentiere ohne das Hauptprojekt zu gefährden
  • Zusammenarbeit - Mehrere Entwickler können parallel arbeiten
  • Industrie-Standard - Wird von fast allen Entwicklern weltweit genutzt

Installation & Setup

Git installieren

macOS

Git ist oft schon vorinstalliert. Prüfe im Terminal:

git --version

Falls nicht installiert, fragt macOS automatisch nach den Xcode Command Line Tools. Alternativ: 

xcode-select --install

Windows

Lade Git von git-scm.com herunter und führe den Installer aus.

Linux (Ubuntu/Debian)

sudo apt update
sudo apt install git

Globale Konfiguration

Nach der Installation musst du Git einmalig konfigurieren:

# Dein Name (erscheint in Commits)
git config --global user.name "Dein Name"

# Deine E-Mail (sollte mit GitHub übereinstimmen)
git config --global user.email "deine@email.com"

# Optional: Standard-Editor setzen
git config --global core.editor "code --wait"  # VS Code

# Optional: Standard-Branch-Name (main statt master)
git config --global init.defaultBranch main

Konfiguration prüfen

# Alle Einstellungen anzeigen
git config --list

# Einzelne Einstellung prüfen
git config user.name
git config user.email

Repository erstellen

Neues Projekt initialisieren

Im Projektordner:

cd /pfad/zu/deinem/projekt
git init

Das erstellt den versteckten .git-Ordner. Dein Projekt ist jetzt ein Git-Repository.

Bestehendes Repository klonen

Ein Projekt von GitHub (oder anderem Server) herunterladen:

git clone https://github.com/username/repository.git

Das erstellt einen neuen Ordner mit dem kompletten Projekt und seiner Git-Historie.

.gitignore einrichten

Die .gitignore-Datei sagt Git, welche Dateien NICHT getrackt werden sollen:

# Dependencies - werden über package.json neu installiert
node_modules/
package-lock.json

# Logs
*.log
npm-debug.log*

# OS-spezifische Dateien
.DS_Store          # macOS
Thumbs.db          # Windows

# Editor-Einstellungen
.vscode/
.idea/
*.swp
*.swo

# Persönliche/temporäre Ordner
-noupload/
README/
temp/
*.tmp

.gitignore Syntax

  • datei.txt - Ignoriert diese spezifische Datei
  • ordner/ - Ignoriert kompletten Ordner (/ am Ende = Verzeichnis)
  • *.log - Ignoriert alle Dateien mit .log-Endung
  • !wichtig.log - Ausnahme: Diese Datei NICHT ignorieren
  • **/temp - Ignoriert "temp" in allen Unterordnern
  • # Kommentar - Kommentarzeile

Die drei Zustände

Git kennt drei Bereiche für deine Dateien:

1. Working Directory

Dein aktueller Projektordner. Hier arbeitest du an deinen Dateien.

2. Staging Area (Index)

Ein Zwischenbereich. Hier sammelst du Änderungen, die in den nächsten Commit sollen.

3. Repository (.git)

Die permanente Git-Datenbank mit allen Commits.

Der Workflow

Working Directory  →  Staging Area  →  Repository
    (bearbeiten)        (git add)       (git commit)

Beispiel:

# 1. Du änderst index.html (Working Directory)

# 2. Du markierst die Änderung für den Commit
git add index.html        # → Staging Area

# 3. Du speicherst den Snapshot permanent
git commit -m "Header aktualisiert"  # → Repository

Grundlegende Befehle

Status prüfen

git status

Zeigt:

  • Geänderte Dateien (rot = nicht staged)
  • Staged Dateien (grün = bereit für Commit)
  • Ungetrackte neue Dateien

Änderungen stagen

# Einzelne Datei stagen
git add datei.html

# Mehrere Dateien
git add datei1.html datei2.css

# Alle Änderungen im aktuellen Ordner
git add .

# Alle Änderungen im gesamten Repository
git add -A

# Interaktiv auswählen
git add -p

Commit erstellen

# Mit Nachricht
git commit -m "Beschreibung der Änderung"

# Staging + Commit in einem (nur für bereits getrackte Dateien)
git commit -am "Alle Änderungen committen"

# Editor öffnen für längere Nachricht
git commit

Gute Commit-Nachrichten

# Schlecht
git commit -m "Update"
git commit -m "Fix"
git commit -m "asdf"

# Gut
git commit -m "Navigation: Dropdown-Menü für mobile Ansicht hinzugefügt"
git commit -m "Bugfix: Sidebar scrollt jetzt korrekt auf kleinen Bildschirmen"
git commit -m "SEO: Meta-Descriptions für alle Tutorial-Seiten ergänzt"

Änderungen ansehen

# Unterschiede im Working Directory (noch nicht staged)
git diff

# Unterschiede in der Staging Area
git diff --staged

# Unterschied zu einem bestimmten Commit
git diff abc123

# Nur Dateinamen anzeigen
git diff --name-only

Staging rückgängig machen

# Datei aus Staging entfernen (Änderungen bleiben erhalten)
git restore --staged datei.html

# Ältere Git-Version
git reset HEAD datei.html

Änderungen verwerfen

# VORSICHT: Verwirft alle Änderungen an der Datei!
git restore datei.html

# Ältere Git-Version
git checkout -- datei.html

Historie & Logs

Commit-Historie anzeigen

# Standard-Log
git log

# Kompakte Einzeiler-Ansicht
git log --oneline

# Mit Grafik für Branches
git log --oneline --graph

# Letzte 5 Commits
git log -5

# Commits einer bestimmten Datei
git log -- datei.html

# Commits mit Änderungen anzeigen
git log -p

# Schöne formatierte Ausgabe
git log --pretty=format:"%h - %an, %ar : %s"

Einzelnen Commit ansehen

# Details eines Commits
git show abc123

# Nur die geänderten Dateien
git show --name-only abc123

Wer hat was geändert?

# Zeigt für jede Zeile, wer sie zuletzt geändert hat
git blame datei.html

# Nur bestimmte Zeilen
git blame -L 10,20 datei.html

Suchen in der Historie

# Commits mit bestimmtem Text in der Nachricht
git log --grep="Navigation"

# Commits die bestimmten Code geändert haben
git log -S "function initSidebar"

# Commits von bestimmtem Autor
git log --author="Dein Name"

# Commits in Zeitraum
git log --since="2024-01-01" --until="2024-12-31"

Branches (Verzweigungen)

Branches ermöglichen parallele Entwicklung. Du kannst an Features arbeiten, ohne den Hauptcode zu beeinflussen.

Branch-Grundlagen

# Alle Branches anzeigen
git branch

# Auch Remote-Branches anzeigen
git branch -a

# Neuen Branch erstellen
git branch feature-navigation

# Zu Branch wechseln
git checkout feature-navigation

# Erstellen + Wechseln in einem
git checkout -b feature-navigation

# Neuere Git-Version (switch statt checkout)
git switch feature-navigation
git switch -c neuer-branch

Branch umbenennen

# Aktuellen Branch umbenennen
git branch -m neuer-name

# Anderen Branch umbenennen
git branch -m alter-name neuer-name

Branch löschen

# Branch löschen (nur wenn gemerged)
git branch -d feature-navigation

# Branch erzwungen löschen (auch wenn nicht gemerged)
git branch -D feature-navigation

Branches zusammenführen (Merge)

# Erst zum Ziel-Branch wechseln
git checkout main

# Dann anderen Branch hineinmergen
git merge feature-navigation

Merge-Konflikte

Wenn beide Branches die gleiche Stelle geändert haben:

<<<<<<< HEAD
Deine Änderung im aktuellen Branch
=======
Änderung aus dem anderen Branch
>>>>>>> feature-navigation

Lösung:

  1. Öffne die Datei und entscheide, welche Version (oder Kombination) richtig ist
  2. Lösche die Konflikt-Marker (<<<, ===, >>>)
  3. Stage die Datei: git add datei.html
  4. Commit: git commit -m "Merge-Konflikt gelöst"

Typischer Branch-Workflow

# 1. Neues Feature starten
git checkout -b feature-search

# 2. Arbeiten und committen
git add .
git commit -m "Suchfunktion: Grundstruktur"
git commit -m "Suchfunktion: Ergebnisanzeige"

# 3. Zurück zum Hauptbranch
git checkout main

# 4. Feature integrieren
git merge feature-search

# 5. Feature-Branch löschen
git branch -d feature-search

Remote Repositories (GitHub)

Ein Remote Repository ist eine Kopie deines Projekts auf einem Server (z.B. GitHub, GitLab, Bitbucket).

Remote hinzufügen

# Remote-Repository verbinden
git remote add origin https://github.com/username/repository.git

# Prüfen welche Remotes existieren
git remote -v

# Remote umbenennen
git remote rename origin hauptserver

# Remote entfernen
git remote remove origin

Pushen (Hochladen)

# Ersten Push (setzt Upstream)
git push -u origin main

# Danach reicht
git push

# Bestimmten Branch pushen
git push origin feature-branch

# Alle Branches pushen
git push --all

Pullen (Herunterladen)

# Änderungen vom Server holen und mergen
git pull

# Nur holen, nicht mergen (sicherer)
git fetch
git merge origin/main

# Mit Rebase statt Merge
git pull --rebase

GitHub Repository erstellen

  1. Auf GitHub einloggen
  2. "New Repository" klicken
  3. Name eingeben (z.B. "DevPanicZone")
  4. Public oder Private wählen
  5. OHNE README erstellen (du hast ja schon Code)
  6. Den angezeigten Befehlen folgen:
# Bestehendes Projekt mit GitHub verbinden
git remote add origin https://github.com/deinname/DevPanicZone.git
git branch -M main
git push -u origin main

SSH vs HTTPS

HTTPS - Einfacher einzurichten, fragt nach Passwort/Token

SSH - Sicherer, keine Passwort-Eingabe nach Setup

# SSH-Key generieren
ssh-keygen -t ed25519 -C "deine@email.com"

# Key anzeigen und auf GitHub hinzufügen
cat ~/.ssh/id_ed25519.pub

# Repository mit SSH klonen
git clone git@github.com:username/repository.git

Rückgängig machen & Wiederherstellen

Letzten Commit korrigieren

# Commit-Nachricht ändern
git commit --amend -m "Neue Nachricht"

# Datei zum letzten Commit hinzufügen
git add vergessene-datei.html
git commit --amend --no-edit

Wichtig: Nur bei lokalen Commits! Gepushte Commits nicht amenden.

Commits rückgängig machen

# Neuen Commit erstellen, der Änderungen rückgängig macht
git revert abc123

# Mehrere Commits reverten
git revert abc123..def456

git revert ist sicher für geteilte Repositories, da es die Historie nicht ändert.

Branch zurücksetzen (VORSICHT!)

# Soft: Commits entfernen, Änderungen behalten (staged)
git reset --soft HEAD~1

# Mixed (Standard): Commits entfernen, Änderungen behalten (unstaged)
git reset HEAD~1

# Hard: Commits UND Änderungen komplett löschen
git reset --hard HEAD~1

# Zu bestimmtem Commit zurück
git reset --hard abc123

WARNUNG: --hard löscht unwiderruflich! Nur bei lokalen, nicht gepushten Commits verwenden.

Gelöschte Commits wiederfinden

# Reflog zeigt ALLE Aktionen, auch "gelöschte" Commits
git reflog

# Zu einem reflog-Eintrag zurück
git reset --hard HEAD@{2}

Einzelne Datei aus Commit wiederherstellen

# Datei aus bestimmtem Commit holen
git checkout abc123 -- datei.html

# Aus letztem Commit
git checkout HEAD -- datei.html

Stashing (Zwischenspeichern)

Stash speichert deine aktuellen Änderungen temporär, damit du den Branch wechseln kannst.

Änderungen stashen

# Änderungen zwischenspeichern
git stash

# Mit Beschreibung
git stash save "Angefangenes Feature"

# Auch ungetrackte Dateien
git stash -u

# Auch ignorierte Dateien
git stash -a

Stash wiederherstellen

# Letzten Stash anwenden und behalten
git stash apply

# Letzten Stash anwenden und löschen
git stash pop

# Bestimmten Stash anwenden
git stash apply stash@{2}

Stashes verwalten

# Alle Stashes anzeigen
git stash list

# Inhalt eines Stash ansehen
git stash show stash@{0}

# Mit Diff
git stash show -p stash@{0}

# Einen Stash löschen
git stash drop stash@{0}

# Alle Stashes löschen
git stash clear

Typischer Stash-Workflow

# Du arbeitest an Feature A, musst aber dringend Bug fixen

# 1. Aktuelle Arbeit zwischenspeichern
git stash save "Feature A - Work in Progress"

# 2. Zum Bugfix-Branch wechseln
git checkout bugfix-branch

# 3. Bug fixen und committen
git commit -am "Kritischen Bug gefixt"

# 4. Zurück zu deinem Feature
git checkout feature-a

# 5. Arbeit wiederherstellen
git stash pop

Tags (Versionen markieren)

Tags markieren wichtige Punkte in der Geschichte, typischerweise Release-Versionen.

Tag erstellen

# Lightweight Tag (nur Marker)
git tag v1.0.0

# Annotated Tag (mit Metadaten) - empfohlen
git tag -a v1.0.0 -m "Version 1.0.0 - Erste stabile Version"

# Tag für älteren Commit
git tag -a v0.9.0 abc123 -m "Beta Release"

Tags anzeigen

# Alle Tags
git tag

# Tags mit Muster
git tag -l "v1.*"

# Tag-Details
git show v1.0.0

Tags pushen

# Einzelnen Tag pushen
git push origin v1.0.0

# Alle Tags pushen
git push origin --tags

Tag löschen

# Lokal löschen
git tag -d v1.0.0

# Remote löschen
git push origin --delete v1.0.0

Semantic Versioning

Empfohlenes Format: vMAJOR.MINOR.PATCH

  • MAJOR - Inkompatible Änderungen
  • MINOR - Neue Features, abwärtskompatibel
  • PATCH - Bugfixes, abwärtskompatibel

Beispiele: v1.0.0, v1.2.3, v2.0.0-beta

Best Practices

Commit-Hygiene

  • Oft committen - Kleine, logische Einheiten
  • Aussagekräftige Nachrichten - Was wurde geändert und warum?
  • Ein Thema pro Commit - Nicht alles vermischen
  • Funktionierenden Code committen - Keine kaputten Zustände

Konventionelle Commit-Nachrichten

feat: Suchfunktion hinzugefügt
fix: Sidebar-Scroll-Bug behoben
docs: README aktualisiert
style: CSS-Formatierung korrigiert
refactor: Navigation-Code vereinfacht
test: Unit-Tests für Search hinzugefügt
chore: Dependencies aktualisiert

Branch-Strategie

  • main oder master - Stabile, produktionsreife Version
  • develop - Entwicklungsversion (optional)
  • feature/name - Neue Features
  • bugfix/name - Bug-Behebungen
  • hotfix/name - Kritische Fixes für Production

.gitignore Grundregeln

  • Dependencies nie committen (node_modules/)
  • Build-Artefakte ignorieren (dist/, build/)
  • Persönliche Einstellungen ignorieren (.vscode/, .idea/)
  • Sensible Daten nie committen (.env, Passwörter)
  • OS-Dateien ignorieren (.DS_Store, Thumbs.db)

Vor dem Push

  1. git status - Was wird committet?
  2. git diff - Änderungen prüfen
  3. git log - Commit-Historie kontrollieren
  4. Code testen - Funktioniert alles?

Git Cheatsheet

Einrichtung

git config --global user.name "Name"
git config --global user.email "email@example.com"
git init
git clone <url>

Tägliche Arbeit

git status                  # Status prüfen
git add .                   # Alles stagen
git commit -m "Nachricht"   # Committen
git push                    # Hochladen
git pull                    # Herunterladen

Branches

git branch                  # Branches anzeigen
git checkout -b name        # Neuer Branch
git checkout main           # Branch wechseln
git merge name              # Branch mergen
git branch -d name          # Branch löschen

Historie

git log --oneline           # Kompakte Historie
git diff                    # Änderungen anzeigen
git blame datei             # Wer hat was geändert

Rückgängig

git restore datei           # Änderungen verwerfen
git restore --staged datei  # Unstagen
git revert abc123           # Commit rückgängig
git stash                   # Zwischenspeichern

Remote

git remote -v               # Remotes anzeigen
git remote add origin url   # Remote hinzufügen
git push -u origin main     # Erster Push
git fetch                   # Änderungen holen

Troubleshooting

Problem: "fatal: not a git repository"

Du bist nicht in einem Git-Repository.

# Lösung: Repository initialisieren
git init

# Oder: In richtiges Verzeichnis wechseln
cd /pfad/zum/projekt

Problem: Merge-Konflikt

# 1. Konflikte in Dateien suchen (markiert mit <<<<<<<)
# 2. Manuell korrigieren
# 3. Datei stagen
git add konflikt-datei.html
# 4. Merge abschließen
git commit

Problem: Falscher Branch

# Änderungen noch nicht committet?
git stash
git checkout richtiger-branch
git stash pop

Problem: Große Datei versehentlich committed

# Aus Historie entfernen (VORSICHT!)
git filter-branch --force --index-filter \
  "git rm --cached --ignore-unmatch pfad/zur/datei" \
  --prune-empty --tag-name-filter cat -- --all

Problem: Push wird abgelehnt

# Jemand hat vor dir gepusht
git pull --rebase
git push

# Oder wenn du sicher bist (VORSICHT!)
git push --force

Problem: Commit-Nachricht falsch

# Letzter Commit, noch nicht gepusht
git commit --amend -m "Richtige Nachricht"

Problem: Alles kaputt, zurück zum letzten funktionierenden Zustand

# Alle Änderungen verwerfen und zum letzten Commit zurück
git reset --hard HEAD

# Zu bestimmtem Commit zurück
git reflog  # Finde den Commit
git reset --hard abc123
